\section{Functional Requirements}

Functional requirements define the specific features and capabilities the Infrastructure Command Center must provide. These requirements were organized around three major feature areas that address the core problems identified in Chapter 1.

\subsection{Dynamic Visual Workflows}

The platform must provide an interactive visual representation of FinGenesis's infrastructure components and their relationships.

\textbf{Requirements:}
\begin{itemize}
    \item Display infrastructure workflows as interactive node-based diagrams
    \item Show connections between services, databases, and external systems
    \item Enable users to zoom, pan, and navigate complex workflow structures
    \item Update visualizations dynamically based on current infrastructure state
    \item Provide clear labels and annotations for each component
    \item Display real-time status indicators for each service 
\end{itemize}

\textbf{Purpose:} Help engineers quickly understand system architecture and dependencies, monitor service health at a glance, and enable faster troubleshooting by immediately identifying which components are experiencing issues.

\subsection{Control Panel}

The platform must provide a centralized interface for managing GitLab repositories and deployment operations.

\textbf{Requirements:}
\begin{itemize}
    \item Display all accessible GitLab repositories in a unified view
    \item Provide search and filtering capabilities (by name, status, deployment state)
    \item Enable sorting by multiple criteria (last updated, pipeline status, repository name)
    \item Allow users to trigger deployments directly from the interface
    \item Support service restart operations without direct GitLab access
    \item Provide merge request management capabilities
    \item Display real-time pipeline status for each repository
\end{itemize}

\textbf{Purpose:} Reduce manual overhead, eliminate context switching between tools, and automate routine deployment operations.

\subsection{ML Metrics Monitoring Section}

The platform must display comprehensive performance metrics for deployed machine learning models.

\textbf{Requirements:}
\begin{itemize}
    \item Visualize model accuracy trends across multiple timeframes (1-minute, 15-minute intervals)
    \item Display prediction quality metrics (MAE, accuracy percentages)
    \item Show performance data for different prediction types (High, Low, Close price predictions)
    \item Support multiple prediction horizons (30 minutes to several hours ahead)
    \item Provide rolling accuracy calculations for smooth trend analysis
    \item Enable drift detection and anomaly identification
    \item Display reference target lines for performance benchmarking
    \item Support configurable time ranges (6 hours, 24 hours, 48 hours, 7 days)
    \item Present current performance summaries with status indicators (healthy, warning, error)
\end{itemize}

\textbf{Purpose:} Enable data scientists and engineers to quickly identify model performance issues, detect drift early, and maintain prediction quality standards.

\section{Non-Functional Requirements}
Non-functional requirements define the quality attributes and constraints that the Infrastructure Command Center must satisfy. These requirements ensure the platform operates reliably, efficiently, and securely in production environments.

\subsection{Performance}

The platform must deliver fast, responsive interactions to support real-time infrastructure management.

\textbf{Requirements:}
\begin{itemize}
    \item Page load times must not exceed 3 seconds under normal network conditions
    \item API responses for common operations (repository listing, metric retrieval) must complete within 2 seconds
    \item Real-time data updates must refresh without noticeable delay or interface freezing
    \item The interface must remain responsive during data loading operations
    \item Chart rendering and visualization updates must complete within 1 second
\end{itemize}

\textbf{Rationale:} Engineers need immediate feedback when managing infrastructure. Delays in displaying critical information or executing operations can impact decision-making and incident response times.

\subsection{Reliability}

The platform must maintain stable operation and handle external service failures gracefully.

\textbf{Requirements:}
\begin{itemize}
    \item System uptime must exceed 99\% during business hours
    \item Integration with GitLab API must handle rate limits and temporary failures without crashing
    \item Prometheus data retrieval must continue functioning even if individual metrics are unavailable
    \item The platform must cache data appropriately to maintain functionality during brief service interruptions
    \item Error states must be clearly communicated to users with actionable recovery steps
\end{itemize}

\textbf{Rationale:} Infrastructure management tools must be dependable. The platform serves as a critical operational interface, and failures would force engineers back to fragmented tools.

\subsection{Scalability}

The platform architecture must accommodate growth in infrastructure complexity and user base.

\textbf{Requirements:}
\begin{itemize}
    \item Support monitoring of 50+ GitLab repositories without performance degradation
    \item Handle concurrent access from 10+ users simultaneously
    \item Process and display metrics for 15+ ML models across multiple timeframes
    \item Backend architecture must support horizontal scaling through containerization
    \item Database and caching strategies must scale with data volume growth
\end{itemize}

\textbf{Rationale:} FinGenesis's infrastructure continues to grow. The platform must scale alongside the organization without requiring fundamental architectural changes.

\subsection{Usability}

The platform must provide an intuitive interface accessible to both technical and non-technical users.

\textbf{Requirements:}
\begin{itemize}
    \item New users must be able to navigate core features without training
    \item Common operations (searching repositories, viewing metrics) must require minimal clicks
    \item Visual design must follow established UI/UX patterns and conventions
    \item Error messages must be clear and provide guidance for resolution
    \item Interface must be consistent across all sections of the platform
    \item Documentation and tooltips must be available for complex features
\end{itemize}

\textbf{Rationale:} The platform's value depends on adoption. If the interface is complex or confusing, users will revert to familiar tools, defeating the purpose of centralization.

\subsection{Maintainability}

The codebase must be organized to facilitate future development and bug fixes.

\textbf{Requirements:}
\begin{itemize}
    \item Code must follow established style guides and conventions
    \item Components must be modular and loosely coupled
    \item API endpoints must be documented with clear request/response schemas
    \item Deployment processes must be automated through CI/CD pipelines
    \item Version control must track all changes with descriptive commit messages
\end{itemize}

\textbf{Rationale:} The platform will evolve over time. Clean, well-organized code ensures that future developers can understand, modify, and extend the system efficiently.

\section{Use Case Identification and Structuring}
Use cases provide a concrete representation of user interactions with \textit{Infra App}, identifying primary actors, their relationships, and the operational scenarios they engage in. This analysis illuminates the system's functional landscape, supporting both design decisions and workflow optimization through proper inheritance and modular design patterns.

\textbf{Stakeholders (Investors/Clients)} can:
\begin{itemize}
    \item View visual workflows to understand system operations, which includes monitoring service status in real-time.
    \item Access MLOps metrics dashboards to track model performance, which includes comprehensive model performance monitoring capabilities.
\end{itemize}

\textbf{Engineers} inherit all Stakeholder capabilities and additionally can:
\begin{itemize}
    \item Manage the GitLab Control Panel, which encompasses:
    \begin{itemize}
        \item Searching repositories across organizational GitLab groups.
        \item Managing CI/CD pipelines for automated deployment workflows.
        \item Managing merge requests (creation, acceptance, and rejection).
        \item Triggering manual jobs for on-demand pipeline execution.
    \end{itemize}
\end{itemize}

\textbf{External System Integration:}
\begin{itemize}
    \item \textbf{GitLab API:} Provides programmatic access to repository management, pipeline control, and merge request operations.
    \item \textbf{Monitoring Systems:} Supply real-time service status data and model performance metrics for operational visibility.
\end{itemize}

This use case structure demonstrates role-based access control through actor generalization, where Engineers inherit read-only monitoring capabilities from Stakeholders while possessing exclusive administrative privileges for GitLab operations. The \texttt{<<include>>} relationships establish mandatory dependencies between composite operations and their constituent tasks, ensuring modular design and clear functional boundaries.

\subsubsection{Deployment Workflow}

Figure 3.2 illustrates the complete deployment workflow, showing the step-by-step process an engineer follows when deploying services through the Control Panel.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{images/activity.png}
    \caption{Deployment Workflow - From Repository Access to Deployment Success}
    \label{fig:deployment_workflow}
\end{figure}

\clearpage
\textbf{Workflow Steps:}

\begin{enumerate}
    \item \textbf{Access Control Panel}: The engineer initiates the workflow by accessing the GitLab Control Panel interface.
    
    \item \textbf{Request Repositories List}: The system requests the complete list of repositories and their current pipeline statuses from the backend.
    
    \item \textbf{Fetch Repository and Pipeline Data}: The backend retrieves repository information and associated pipeline data through the GitLab API.
    
    \item \textbf{Display Repositories with Actions}: The Control Panel displays all repositories with their current status, branch information, and available actions based on their state.
    
    \item \textbf{View Repository List}: The engineer reviews the displayed repositories to identify the target service for deployment.
    
    \item \textbf{Main Branch Decision Point}: The system evaluates whether the repository is on the main branch:
    \begin{itemize}
        \item \textbf{If No}: The workflow ends, as deployment actions are only available for main branch repositories.
        \item \textbf{If Yes}: The workflow proceeds to check for available deployment jobs.
    \end{itemize}
    
    \item \textbf{Manual Job Availability Check}: The system determines whether manual deployment jobs are available for the repository:
    \begin{itemize}
        \item \textbf{If Already Deployed}: The system displays "Already Deployed" status, indicating no action is needed.
        \item \textbf{If Manual Job Available}: The system displays the "Deploy" button, enabling the engineer to trigger deployment.
    \end{itemize}
    
    \item \textbf{Click Deploy Button}: The engineer initiates deployment by clicking the Deploy button.
    
    \item \textbf{Request Manual Jobs List}: The backend queries the GitLab API to retrieve the list of manual jobs associated with the repository's pipeline.
    
    \item \textbf{Query Manual Jobs}: The GitLab API returns available manual jobs that can be triggered.
    
    \item \textbf{Select Deploy Job}: The system identifies the appropriate deployment job from the manual jobs list.
    
    \item \textbf{Trigger Selected Job}: The backend sends a request to the GitLab API to execute the selected deployment job.
    
    \item \textbf{Execute Deployment Job}: The GitLab API initiates the deployment pipeline, beginning the deployment process.
    
    \item \textbf{Deployment Started}: The GitLab API confirms that the deployment job has been successfully triggered.
    
    \item \textbf{Success Notification}: The engineer receives a success notification in the Control Panel, confirming that deployment has been initiated.
    
    \item \textbf{End}: The workflow completes successfully with the deployment in progress.
\end{enumerate}

This workflow demonstrates the intelligent decision-making embedded in the Control Panel, which automatically determines available actions based on repository state (branch, pipeline status, existing deployments) and guides engineers through the deployment process with minimal manual steps.

\subsubsection{Repository Data Retrieval and Deployment Sequence}

Figure 3.3 presents a detailed sequence diagram showing the interactions between system components during repository data retrieval and deployment operations, highlighting the caching strategy and parallel API calls.

\begin{sidewaysfigure}
    \centering
    \includegraphics[width=\textwidth]{images/sequence.png}
    \caption{Sequence Diagram - Repository Retrieval and Deployment Flow}
    \label{fig:deployment_sequence}
\end{sidewaysfigure}

\textbf{Phase 1: Repository Data Retrieval (Steps 1-13)}

\begin{enumerate}
    \item \textbf{View Repositories Request}: The engineer initiates repository viewing by accessing the Control Panel interface.
    
    \item \textbf{GET /gitlab/data}: The frontend sends an HTTP GET request to the backend to retrieve repository data.
    
    \item \textbf{Check Cache}: The backend checks if repository data exists in the cache (populated by the background refresh task that runs every 10 seconds).
    
    \item \textbf{Cache Miss}: If the cache is empty or outdated, the system proceeds to fetch fresh data from external services.
    
    \item \textbf{Fetch Repos}: The backend initiates a request to the GitLab Service to retrieve repository information.
    
    \item \textbf{GET /projects}: The GitLab Service sends a request to the GitLab API to retrieve all accessible projects within the configured groups.
    
    \item \textbf{Repo Data}: The GitLab API returns the list of projects with their basic information (name, ID, description, last activity).
    
    \item \textbf{GET /pipelines}: In parallel with project retrieval, the GitLab Service requests pipeline status information for each repository.
    
    \item \textbf{Pipeline Data}: The GitLab API returns pipeline information (status, branch, stage, job details) for each project.
    
    \item \textbf{Formatted Data}: The backend processes and formats the combined repository and pipeline data into a unified structure suitable for frontend consumption.
    
    \item \textbf{Store in Cache}: The formatted data is stored in the cache, ensuring subsequent requests receive instant responses without additional API calls.
    
    \item \textbf{JSON Response}: The backend returns the complete repository data to the frontend as a JSON response.
    
    \item \textbf{Display Repos}: The frontend renders the repository list in the Control Panel, showing all available information and actionable buttons.
\end{enumerate}

\textbf{Phase 2: Deployment Triggering (Steps 14-22)}

\begin{enumerate}
    \setcounter{enumi}{13}
    \item \textbf{Click "Deploy"}: The engineer clicks the Deploy button for a repository on the main branch with passed pipelines.
    
    \item \textbf{POST /gitlab/trigger}: The frontend sends a POST request to the backend to initiate the deployment process.
    
    \item \textbf{Get Manual Jobs}: The backend requests the list of manual jobs available for the selected repository's latest pipeline.
    
    \item \textbf{GET /jobs?scope=manual}: The GitLab Service queries the GitLab API specifically for jobs with manual scope (jobs that require explicit triggering).
    
    \item \textbf{Manual Jobs List}: The GitLab API returns the list of manual jobs, typically including deployment jobs that must be triggered explicitly.
    
    \item \textbf{POST /jobs/:id/play}: The backend identifies the deployment job from the manual jobs list and sends a request to execute it by ID.
    
    \item \textbf{Success}: The GitLab API confirms successful job execution, indicating the deployment pipeline has started.
    
    \item \textbf{Deployment Started}: The backend returns a success response to the frontend, confirming deployment initiation.
    
    \item \textbf{Success Message}: The frontend displays a success notification to the engineer, and the repository status updates to reflect the ongoing deployment.
\end{enumerate}

\textbf{Key Architectural Patterns Demonstrated:}

\begin{itemize}
    \item \textbf{Caching Strategy}: The system checks cache before making external API calls, dramatically reducing response times (from seconds to milliseconds) and minimizing load on GitLab's API.
    \item \textbf{Parallel API Calls}: Repository and pipeline data are fetched simultaneously rather than sequentially, reducing total retrieval time by approximately 50\%.
    \item \textbf{Background Refresh}: The 10-second background task keeps cache fresh, ensuring users always see recent data without waiting for API calls.
    \item \textbf{Separation of Concerns}: The GitLab Service abstracts API communication, allowing the backend to focus on business logic and caching while the service handles external integration details.
    \item \textbf{Asynchronous Processing}: All external API calls use async/await patterns, preventing interface freezing and enabling concurrent operations.
\end{itemize}

These interaction flows demonstrate how the Infrastructure Command Center efficiently orchestrates complex operations while maintaining responsiveness and reliability through intelligent caching, parallel execution, and clear separation between system components.
